# Read tier — AXVERITY_READ_INDEX_RAM_TIER_V1 + AXVERITY_FORMAT_LAND_AND_WIRE_V1

A name-index, three adjacency projections, and a traversal read API over them,
plus a cold rebuild of all of it from the durable store — **both streams**, not
the structure stream alone. See "the rebuild reads BOTH streams" below; several
statements in this file predate that fix and are marked where they appear.

**Still unwired, and it turned out not to need wiring.** It links into its own
binary from its own sources and its own registry, and nothing in the `wp_*`
write path references it or is referenced by it. What P3 established is that
this is not a gap: the read tier reads the DURABLE STORE, which is a shared
artefact rather than a channel, so no tap into the pipeline is required and the
write path was not modified to connect them.

The RAM structures themselves still touch no filesystem — that is why peak RSS
is read from outside the process. The durable tier (`rt_rebuild`, point reads)
is the part that opens files, and it is separate by construction.

## Shape

**Name-index (W1).** `name -> internal id`. Two Text maps and one u32 array:
`head` (name -> newest id), `name` (id -> name), and `prev`, a dense u32 array
indexed BY id holding `superseded id + 1` (0 terminates the chain). Inserting a
name that already exists *pushes*: the new id becomes the head and the old one
is retained behind it. `rt_nidx_resolve` is get-or-insert and does not
supersede; `rt_nidx_insert` always supersedes. Ids are dense internal integers
— **not** RIDs, no physical meaning — and the array's own length is the id
counter, so there is no separate `meta` map.

The dictionary is PROCESS-LOCAL: built at cold start, dead at exit, never
durable and never on the wire. IDENTITY_IS_A_NAME_NOT_A_HASH is untouched by
that — the store still stores names; an id is a handle, not an identity.

**Three projections (W2).** One minimum prefix cover, the cyclic one:

| store | ordering | sort key | prefix-serves |
|---|---|---|---|
| `rt:A` | S,V,T | `(0,1,2)` | `???` `S??` `SV?` `SVT` |
| `rt:B` | V,T,S | `(1,2,0)` | `???` `?V?` `?VT` `SVT` |
| `rt:C` | T,S,V | `(2,0,1)` | `???` `??T` `S?T` `SVT` |

Union is all eight. Three is the combinatorial minimum: each ordering covers one
singleton and one pair, and there are three of each, so no two orderings reach
all eight. The other valid minimum cover is the reverse cycle STV/VST/TVS.

Each projection is ONE `u32v` at stride 3 — a named, growable, append-only
`Vec<u32>` (`u32v.rs`). **All three hold the identical record `(s, v, t)` in
that slot order**; the only thing that distinguishes them is the permutation
passed to `u32v_sort3`. THE KEY ORDER IS THE ROTATION, and it lives in the sort
key and nowhere else — which is why nothing downstream permutes a tuple back
into canonical form.

APPEND_ONLY_PLUS_SEALED_SORT. `rt_index_triple` only pushes. `rt_seal` does the
one in-place reordering, lazily, at the first read after a write; its dirty test
is `u32v_len != the length last sorted`, so the ingest path carries no flag
write. There is no set, no remove and no truncate on the surface, so a triple
indexed twice occupies two records for the life of the process and dedup happens
on the way OUT — **by ADJACENCY, not by hash** (Phase A,
`AXVERITY_READTIER_READPATH_LATENCY_V1`). `u32v_sort3` keys on all three slots,
so the comparison is total over the record and identical records land
CONSECUTIVELY (`u32v.rs:200-206`, comparator at `u32v.rs:240-242`); a scan walks one CONTIGUOUS range of a sealed
array, so a duplicate can only arrive immediately after the record it
duplicates. One three-slot compare against the previous record replaces the
Text-keyed `set_add` probe that used to do this.

**Traversal (W3).** `rt_query(mask, s, v, t)`, mask 1=S 2=V 4=T, plus eight
direct entry points. Every pattern routes to the projection whose sort key
serves it and becomes ONE call: `rt_range(store, nk, q0, q1, q2)`. A range is
two M1-side binary searches — lower bound of the prefix, lower bound of the
prefix with its last bound component incremented — and the records between them
are the answer. `end - start` is the record count, free and without
materialisation; it differs from the ANSWER's cardinality exactly by the
duplicates in the range.

The fully-bound pattern is no longer a special case: `SVT` is a range of at most
one record, found by the same two bounds as the others. The trie needed a
distinct membership probe against its leaf set; a sorted array does not, because
a fully-bound key is just the narrowest prefix.

An unknown name resolves to `-1`, which sorts below every stored id, so both
bounds land together and the answer is empty **without a branch** — the same
arithmetic in all eight patterns rather than a special case that could be
forgotten in one.

`loop_while`'s cond and step are Fn REFERENCES resolved at emit time
(`iter.rs:3-7`), so the array a probe reads cannot be selected at runtime.
Hence one probe fn and one scan fn per projection (`rt_bs_a/b/c`,
`rt_sc_a/b/c`) with `rt_lb` / `rt_scan` as dispatchers. The alternative —
reading the array name from a scratch map on every probe — is two Text literals
plus a hash lookup, ~60 ns on top of ~90 ns of real work, on the one path this
rewrite exists to make cheap.

Results land in a named result store read via `rt_out_count` / `rt_out_at` /
`rt_out_has` — **not** as an M1 list, because building a list by repeated
`list_append` names the accumulating list at every call site and every mention
of a list is a deep copy, making an R-element result O(R²).

**`rt:out` is a fourth `u32v`** (Phase A). It was a Text-keyed set for
membership plus an integer-slotted Text map for ordinal access, which meant
every result was rendered to decimal, glued into a separator-joined key and
hashed twice — **23 heap allocations per result**, counted from the emitted
glue and confirmed by measurement, whether or not the caller ever read the
result back. It is now stride 3 and filled by `u32v_push`, and the EMIT cost is
**2 allocations**: one pool literal in `rt_sc_a` and one in `rt_out_emit`, and
nothing else.

**THE RENDER DID NOT DIE, IT MOVED.** `rt_out_at` renders on demand, so a
count-only caller pays nothing per result — but a STREAMING consumer, which is
what `sh_query_step` and therefore every wire client is, walks every element
through it and pays the `int_to_str` × 3 and the `rt_key3` there instead.
Measured end to end over the wire, the saving is **8.0 allocations per row, not
22.3**. Both numbers are below, and the streaming one is the one that describes
a deployment.

**The result set is sealed with `u32v_sort3(0, 1, 2)` — but only for `?V?`.**
The seal is what makes the ANSWER's order a property of the answer rather than
of the projection that served it: every pattern hands back ascending canonical
`(s, v, t)`, and `rt_out_has` can binary-search. Seven of the eight patterns get
that for free, because a range is a contiguous slice of a sealed projection and
adjacency dedup only drops elements. Fix the bound components and read what is
left of each sort key:

| store | key | bound | range order | canonical? | patterns |
|---|---|---|---|---|---|
| `rt:A` | `(s,v,t)` | anything | `(s,v,t)` | yes | `???` `S??` `SV?` `SVT` |
| `rt:C` | `(t,s,v)` | `t` | `(s,v)` | yes | `??T` `S?T` |
| `rt:B` | `(v,t,s)` | `v`,`t` | `(s)` | yes | `?VT` |
| `rt:B` | `(v,t,s)` | `v` only | `(t,s)` | **no** | `?V?` |

So the guard is `store == rt:B && nk == 1`, and `rt:B` is never reached with
`nk` 0 or 3. `rt_out_has` is unaffected either way: the array is sorted on
arrival on the seven, and by the call on the eighth.

`rt_out_has` parses the canonical key back to three ids and binary-searches the
sealed array (`rt_bs_o` / `rt_lb_o`, the fourth member of the `rt_bs_*`
family). It is reached only from the assertion suites.

### U5 — is the five-call `u32v` surface sufficient? Qualified yes.

Sufficient for the ARRAY, and only for the array. `u32v_new` / `push` establish
and fill it, `sort3` seals it, `get` / `len` read it. No sixth `u32v` call was
needed and none was added.

Phase A of `AXVERITY_READTIER_READPATH_LATENCY_V1` re-asked the question against
a fourth array with a different shape — a RESULT set, rebuilt per query rather
than once per process, read by ordinal and by membership — and the answer held:
`rt:out` needs `new`, `push`, `sort3`, `get`, `len` and nothing else. Stop
condition S1 was not reached.

**But the search is not expressible in those five.** Composing them into a
range lookup depends on pre-existing bridge primitives that do the work `u32v`
deliberately has no opinion about:

| | why it is load-bearing |
|---|---|
| `loop_while` | M1 has no loop. A binary search is `log2(n)` iterations of a shrinking window. |
| `mem_reserve_raw` / `mem_free_raw` | somewhere to put that window |
| `mem_read_int_raw` / `mem_write_int_raw` | reading and narrowing it |
| `tuple_field` | unpacking the reservation |

The reason it cannot be done without raw scratch is written out in
`rt_bs_more.m1`: `loop_while` CLONES its accumulator on every iteration
(`iter.rs:78`), so state carried in the accumulator is copied per probe. An
`Int` pointer clones for free; the window it points at does not move.

### Substrate invariants this tier leans on

Two properties of the toolchain, neither of which this tier can assert and both
of which it would silently mis-perform without. Written down because a change
to either would leave **all 98 assertions passing** while the performance
claims above quietly became false.

**`if` IS LAZY — an untaken branch does not execute.** Verified in the emitter,
not inferred from timings: `axis-codegen-bridge-rs/src/emit/rust_05.rs:1602-1618`
renders each branch's scope INSIDE a real Rust `if`/`else`, and the emitted
glue shows it — `readtier/build/generated_rt_seal_xb.rs` has all three
`u32v_sort3` calls nested in the `else` arm.

Three things depend on it. `rt_seal` would sort three arrays on EVERY query
rather than on the first after a write. `rt_range` would run `rt_hit` and
`rt_ub` both, taxing seven patterns with the eighth's work. And `rt_bs_*`'s
short-circuit would read all three slots per probe. None of that changes an
ANSWER — which is exactly why the test suite could not catch it.

**A `Text` literal is a heap allocation, once per call, whether or not its
branch is taken.** `intern_str` is `Arc::from` (`runtime/value.rs:152-154`), and
the constant pool is built at fn entry ahead of any branch. This is why
`rt_bs_a/_b/_c` and `rt_sc_a/_b/_c` exist as one file per array — a literal in
a `loop_while` step is an allocation per probe — and why `rt_vget`, which
carries all three, is confined to the once-per-query path.

No limit was broken — these are long-standing bridge primitives, not a sixth
`u32v` call. But "five calls sufficed" would read in six months as *the `u32v`
surface is self-sufficient*, and it is not. It is sufficient **given** a raw
scratch cell and a bounded loop.

## Measured (AXVERITY_READTIER_READPATH_LATENCY_V1)

Phase A rewrote `rt:out`. Phase B priced the dictionary lookups off the ladder
the rewrite left behind. Everything below is ONE session, back to back, on one
machine: the pre-Phase-A binary was kept and re-run interleaved with the new
one, so the two columns may be read against each other and nothing here may be
read against the section above it.

**Allocation counts are the primary evidence and ns corroborates**, because an
allocation count is deterministic and a nanosecond is not. Counts come from an
`LD_PRELOAD` interposer on `malloc`/`calloc`/`realloc` (this machine has no
valgrind); it touches no repo file and no bridge file.

| **accounted** | **21** | |
| unattributed | **1.3** | most likely `format!`'s buffer growth inside `str_concat`; it is 6% of the total and this instrument cannot split it |

What survives is **2 allocations per result** — `Text("rt:A")` in `rt_sc_a` and

`build/generated_rt_sc_a_xb.rs:17` and `build/generated_rt_out_emit_xb.rs:24`.
The three `u32v_get` share the first pool literal and the three `u32v_push`
share the second, so widening the record would not add allocations.

**And now the number that describes a deployment.** 22.3 is the COUNT-ONLY
path. `sh_query_step.m1:19` — the only caller that reads more than ordinal 0,
and the one every wire client goes through — walks every element through
`rt_out_at`, which is where the `int_to_str` × 3 and the `rt_key3` went. So the
render was moved off the emit path and onto the read path, not deleted.

Measured over the wire rather than derived: a `QUERY` streaming `???` over a
4,000-triple store, allocations counted in the SHIM process, sloped across four
row counts so the connection, the rebuild and the query setup fall out. Both
shims were built — the pre-Phase-A tier and this one — because the shim's own
per-row work (`sh_name3`, framing, the socket) is identical across them and
cancels in the difference.

| rows streamed | 20,000 | 80,000 | 140,000 | 200,000 | slope |
|---|---|---|---|---|---|
| before | 2,214,830 | 8,035,535 | 13,856,240 | 19,676,945 | **97.012 /row** |
| after | 2,054,751 | 7,395,231 | 12,735,711 | 18,076,191 | **89.008 /row** |

Exactly linear — the slope is identical to three decimal places across all
three intervals, which is what a deterministic per-row cost looks like.

**8.0 allocations removed per row, −8.3%. 14.3 of the 22.3 come back** the
moment a consumer reads its results. The count-only figure is not wrong, it is
the wrong question for a streaming client, and real consumers stream.

Two things that follow, and neither is measured here. Most of those 89 are the

`u32`-shaped wire, or a client that asks for ids rather than names, would take
the render out entirely. Both are DERIVED, and both are somebody else's gate.

`realloc` collapses with them: 476,417 → 4,473 at n=65,536, because the growing
Text-keyed slot map is gone and a `Vec<u32>` doubles.

`pop` is unchanged — 2,392,399 → 2,392,396 allocations at n=65,536, a
three-allocation difference that is `rt_out_reset` itself. The ingest path was
not touched.

### What the seal costs, isolated

An earlier draft of this file derived the seal's cost by subtracting `???`'s
580 ns/result from `?V?`'s 599 and calling the 19 ns a measurement. It was not
one: those two patterns differ in projection, in scan length and in result
count (149,796 against 1,048,576), so their cache behaviour differs entirely.
The number is now taken by SINGLE-VARIABLE A/B — the same tree built twice with
one literal different, so that the guard is never true and nothing is sorted.
The probe's output order is wrong by construction; it is a cost probe and was
never a candidate to ship.

| pattern | n | card | shipped | never sorts | seal, ns/result |
|---|---|---|---|---|---|
| `?V?` — GENUINE re-sort | 16,384 | 2,340 | 579 | 574 | +5 |
| `?V?` | 262,144 | 37,449 | 586 | 569 | +17 |
| `?V?` | 1,048,576 | 149,796 | 593 | 577 | +16 |
| `???` — CONTROL, neither build sorts it | 16,384 | 16,384 | 556 | 572 | −16 |
| `???` — control | 262,144 | 262,144 | 556 | 569 | −13 |
| `???` — control | 1,048,576 | 1,048,576 | 574 | 574 | 0 |

**Read the control row first.** `???` is skipped by both binaries, so its true
difference is zero, and it measures −16, −13 and 0. **That is the noise floor
of this comparison: ±16 ns per result.** The genuine re-sort measures +5, +17
and +16 against it.

So: **a genuine canonical re-sort of up to 149,796 results costs ≲20 ns per
result, and this instrument cannot resolve it more finely than that.** The
suspicion that 150k elements at ~17 comparisons each must cost far more than
that does not survive the measurement — a `sort_unstable_by` over a
cache-resident 1.8 MB array of `[u32; 3]` runs at about a nanosecond per
comparison. The old 19 ns landed near the isolated figure, and that is a
coincidence, not corroboration; the method was wrong and is retired.

Sorted input is cheaper still and is at or under the same floor: comparing the
unconditional-seal build against the guarded one, `???` at 1,048,576 moves 580
→ 556 ns/result while `?V?` — which sorts in both — moves 599 → 587. The
difference of differences is ~12 ns/result, inside ±16.

### The guard is nearly free and the sort it skips was nearly free too

Skipping a provably unnecessary `sort_unstable_by` over a million records ought
to be a large win. It is not, and the measurement says so in two directions.

**First, the guard is not free unless it is written lazily.** `bool_and` is a
CCall, so BOTH its arguments are evaluated: `bool_and(int_eq(store, 1),
int_eq(nk, 1))` is three bridge crossings on every query. Nested `if`s are lazy
(`emit/rust_05.rs:1601-1618`), so the six patterns served by `rt:A` and `rt:C`
pay one `int_eq` and stop. Both forms were built and laddered against the
unconditional seal, nine populations, five runs each, six constant-cardinality
patterns — 54 comparisons per form:

| guard form | median Δ vs unconditional seal | positive |
|---|---|---|
| `bool_and`, 3 crossings always | **+277 ns/op** | 52 / 54 |
| nested `if`, 1 crossing on `rt:A` / `rt:C` | **+9 ns/op** (mean −5) | 29 / 54 |

Head to head the nested form is faster on **53 of 54** by a median of 275 ns.
So ~277 ns is what two extra bridge crossings cost on this path — about 138 ns
each, against the ~30 ns marginal `u32v_get` the U6 bench measures inside a
tight loop. It is not build layout: changing only the guard's shape moved it.
**The lazy form is what ships.**

**Second, the win it was reaching for is inside the noise.** The sorted-input
sort that the guard removes from seven patterns costs ~12 ns/result at best
(above), against a ±16 ns/result floor. `???` at 1M was predicted to move and
it moved 580 → 556, which is one noise width. The guard is kept because it
removes work that is provably unnecessary and, written lazily, costs nothing
measurable — **not because it bought anything.** That is the same standard the
dead successor-key bump was kept under one intent ago, and it is stated the
same way on purpose.

### T3 — the ordering change, enumerated and then measured

### Phase B — pricing a bound name, and why the answer is a bound and not a number

The eight patterns bind 0, 1, 2 or 3 names. Grouping their fitted intercepts
against bound-name count is supposed to give the per-name lookup cost as a
slope. **It does not, and the reason is structural rather than a shortage of
runs.** This is stop condition S3.

Fits are `ns/op = A + σ × probes`, `probes = searches × log2(n)`, over nine
populations 16 … 1,048,576, five runs each, medians:

| pattern | names | card | searches | A before | A after | σ before | σ after |
|---|---|---|---|---|---|---|---|
| `S??` | 1 | 4 | 2 | 8,152 | 6,208 | 202.7 | 192.1 |
| `??T` | 1 | 4 | 2 | 7,806 | 5,805 | 227.5 | 211.0 |
| `SV?` | 2 | 1 | 2 | 5,009 | 4,410 | 207.2 | 203.4 |
| `?VT` | 2 | 1 | 2 | 4,551 | 4,000 | 260.6 | 253.7 |
| `S?T` | 2 | 1 | 2 | 5,027 | 4,508 | 212.6 | 200.9 |
| `SVT` | 3 | 1 | 1 | 5,774 | 5,231 | 208.5 | 203.1 |

**The per-probe slope survives everything.** 202.7 / 207.2 / 212.6 / 208.5
before and 192.1 / 203.4 / 200.9 / 203.1 after, against the predecessor's 199 /
202 / 203 / 203.5 / 206 / 207 across five earlier builds. Phase A did not touch
the search and the search did not move. (`??T` and `?VT` sit high at 227 and
254–260 in both columns; they are the two patterns whose second search runs over
a window this model does not describe, and the excess is in the same direction
in both columns.)

**Two things are measured cleanly.** First, the per-RESULT cost, and it needs no
fit at all: `?V?`, `S??` and `??T` all bind one name and run two searches, so at
a matched population the difference between them is purely results.

| n | 64 | 256 | 1k | 4k | 16k | 64k | 256k | 1M |
|---|---|---|---|---|---|---|---|---|
| `(?V? − S??) / (card − 4)` before | 1,282 | 1,267 | 1,204 | 1,186 | 1,194 | 1,216 | 1,256 | 1,486 |
| after | 504 | 608 | 599 | 588 | 599 | 597 | 596 | 599 |

Second, the fully-bound pattern's intercept step:
`A(SVT) − mean A(2-name)` is **911 before and 925 after** — two separately
compiled binaries, ten runs, agreeing to 14 ns.

**What is not measured is L, the per-bound-name cost**, and three independent
routes to it disagree by more than the quantity itself:

| route | before | after | should be |
|---|---|---|---|
| `3R − dA`, with R from the table above | 483 | 93 | identical — the dictionary path is byte-identical across Phase A |
| `A(SVT) − A(2-name)` | 911 | 925 | confounded: it is `L + rt_hit − s₂ − rt_ub`, and `rt_hit` alone is derived at ~430 ns |
| `rt_bench_nidx`, standalone, this session | 426 | 426 | a lookup with no query around it |

The first route is the one the intent named, and it fails its own invariance
check by 390 ns. The reason is arithmetic: `dA` confounds one lookup with THREE
results, so a 130 ns error in R — well inside what the table above varies by —
becomes a 390 ns error in L. And 390 ns is not distinguishable here, because
**patterns that bind the SAME number of names and run the SAME number of
searches have intercepts 346 to 508 ns apart**: `S??` vs `??T` differ by 346
(before) and 403 (after); `SV?` / `?VT` / `S?T` span 476 and 508.

**No two of the eight patterns differ ONLY in bound-name count.** Binding one
more name always also changes the result count, or the search count, or both.
That is a property of the eight binding patterns, not of this ladder, and no
number of extra runs fixes it.

**And the method's premise is false anyway: a lookup is not a
population-independent cost.** `rt_bench_nidx` measures it standalone at every
rung, three runs, medians:

| n | 16 | 64 | 256 | 1k | 4k | 16k | 64k | 256k | 1M |
|---|---|---|---|---|---|---|---|---|---|
| lookup, ns/op | 331 | 296 | 287 | **284** | 293 | 301 | 342 | 394 | **436** |
| insert, ns/op | 1,093 | 959 | 979 | 926 | 1,000 | 992 | 1,051 | 1,378 | 1,548 |

**+152 ns, +54%, from 1,024 names to 1,048,576.** A `HashMap<String, Arc<str>>`
at half a million entries misses cache where one at a thousand does not. So
"the slope of intercept against bound-name count" is asking a fitted INTERCEPT
— a quantity extrapolated to n = 1 — to report a cost that only exists at
scale, and whatever drift there is gets charged to σ instead. This is not a
correctable flaw in the fit. It is the wrong instrument for the question.

**Verdict: L is bounded, not measured. It lies somewhere in ~90–930 ns, with
426 ns measured standalone in the same session and nothing on the query path
contradicting it.** `MEASURE_BEFORE_PRIMITIVE` is therefore not satisfied, and
`s2i` is not warranted on this evidence. See the recommendation below.

### T5 — the 965 ns/result figure, corrected

The predecessor read the `S??` / `SVT` intercept gap of 2,895 ns as "`S??`'s
three extra results at ~965 ns each". The identity is not `gap = 3R`. Both
patterns were two-search at the time, so

    A(S??) − A(SVT)  =  (B + L + 4R) − (B + 3L + R)  =  3R − 2L

and dividing by three estimates `R − ⅔L`, not `R`. With this session's
before-column numbers, `R = 1,200` and `L` no worse than ~430, that identity
predicts `1,200 − 287 = 913` against the 965 that was reported — so **the old
figure was low by roughly one bound name's worth divided by three, and it
happened to be only ~5% wrong because `⅔L` is small next to `R`.** The right
value of R is not 965: it is **1,186–1,282 ns/result**, measured directly at
seven populations and quoted above with no fit in it.

The gap is no longer even that identity. F1 made `SVT` a ONE-search pattern, so
`A(S??) − A(SVT)` now also carries a whole search's residual: 2,379 before and
977 after, and `gap / 3` — 793 and 326 — estimates nothing at all. Read the
direct per-result table instead.

### The `s2i` recommendation

**Do not build it yet.** Not because the idea is wrong — the dictionary is
`HashMap<String, Arc<str>>` holding decimal renderings of integers, and
`rt_nidx_lookup` really does `map_get` → `str_eq` → `str_to_int` on every bound
name of every query — but because this intent's own gate was not met. The
measurement that was supposed to name the primitive came back unresolvable, and
building on `426 ns standalone` while the on-path figure is bounded only to
90–930 would be exactly the "implementation of a guess" the risk register calls
unacceptable.

**What the measurement DID find is a better argument for `s2i` than the one the
intent carried in.** The case was "426 ns per bound name, and a third of it is
render/parse." The measured case is that the lookup **grows with the
dictionary** — 284 ns at a thousand names, 436 at a million — because the thing
being probed is a `HashMap<String, …>` whose keys are decimal renderings of
integers, three to seven bytes each, at 48% load. That is a cache-residency
argument, and it says the win is largest exactly where the tier is going. It
also says a `u32`-valued map is only half the fix: the KEY is still a `String`
and still hashed. Whatever is designed at Phase C should be priced against
that curve, not against a single number.

What would settle it, and it is one measurement rather than a design: a query
whose bound names are UNKNOWN. `rt_nidx_lookup` returns −1 without the
`str_to_int`, both bounds collapse and the answer is empty, so the patterns
differ in bound-name count with no result term at all. `rt_bench_step`
synthesises its names from the population and cannot ask for one that was never
inserted; making it able to is a change to the benchmark harness, which this
gate did not authorise.

**The pair is `S??` and `SV?`, and `SVT` must NOT be in it.** Both of the first
two run two searches and return zero rows, so one binds one name and the other
binds two and nothing else differs — the difference IS L. `SVT` binds three but
F1 made it a ONE-search pattern, so putting it in the design reintroduces
exactly the search-count confound that killed route 2 above. Drop it.

**One residue survives even in the surviving pair, and it is named now so it is
not re-derived at the next gate.** An unknown name resolves to −1, so `S??`
searches for `(−1, 0, 0)` and its successor `(0, 0, 0)`, while `SV?` searches
for `(−1, −1, 0)` and `(−1, 0, 0)`. `S??`'s second bound TIES on slot 0 whenever
a record's `s` is 0 and falls through to the second and third `u32v_get`;
`SV?`'s bounds never tie, because no stored id is negative. So `S??` pays 1–3
gets on some probes of its second search where `SV?` pays exactly 1. At ~30 ns
a get and a handful of tying probes per search that is tens of ns, small next
to any plausible L — but it is a bias in a known direction and it should be
subtracted rather than discovered.

**278 is above this intent's ~200 B/triple stop condition, and the decomposition
says the stop condition's stated implication is false.** It is not "something
other than the text keys": it is the text keys, plus the benchmark harness's own
loop. Measured, not computed — `popvec` builds the projections with no
dictionary, `popidx` builds the dictionary with no projections, `poploop` runs
the population loop with an empty body:

| component | 100k | 1M |
|---|---|---|
| harness `foreach(range(0,n))` | 17 | 59 |
| three projections (`u32v`) | 37 | **36** |
| dictionary (two Text maps) | 120 | 168 |
| unattributed residual (see below) | 16 | 15 |
| measured whole (`pop`) | 190 | 278 |

**What `popvec` does and does not establish.** It mints ids arithmetically
instead of resolving names, so it reproduces the record COUNT and the
per-column CARDINALITY of a real build. It does **not** reproduce the
distribution: real minting interleaves by first appearance (i=0 gives
s=0, v=1, t=2), while `rt_pop_vec_step` hands out blocked ranges. That is
harmless for a footprint, which depends on how many u32 exist and not on their
order. It would be **invalid for any sort-timing claim** — presortedness is
exactly what makes rt:A's own sort number an artefact, and this arm arranges
the input differently from the thing it stands in for. Footprint only.

The projections landed at **36 B/triple** — 12 bytes per record per array,
exactly three u32 with no slack, because a `Vec`'s reserved-but-untouched
capacity is never faulted in. That is the ~40 B/triple this rewrite targeted,
and it is between Ring's 12.7 and QLever's 24-per-permutation (72 for three).

The dictionary is 168 B/triple = **336 bytes per distinct name** across two
`HashMap<String, Arc<str>>` — a String key, an `Arc<str>` value, and hashbrown's
power-of-two table sitting at 48% load at 500,007 names. It was never in this
intent's scope to change, and the reverse map (`id -> name`) that is half of it
is reachable only from the W1 assertions.

**The residual is glibc's dynamic mmap threshold, and it is 15 B/triple.**
The parts sum to 263 against a measured 278 at 1M, and to 174 against 190 at
100k — ~15 B/triple at both decades, so it is proportional and not a one-off
transient. Sum-of-parts should if anything EXCEED the whole, since separate
arms each capture their own peak and those peaks need not coincide. It is
under, so something in `pop` costs more than the parts predict.

Not per-iteration string churn. That hypothesis does not survive the
arithmetic: `X = pop − popvec − popidx + poploop`, and `rt_pop_idx_step` does
the identical `map_get` + `str_to_int` + 3×`int_to_str` + 3×`str_concat` that
`rt_pop_step` does, so the churn appears once in `popidx` and once in `pop` and
cancels — if anything contributing NEGATIVELY through `popvec`'s partial share.

Measured instead, by pinning the allocator (env only, no code change):

| case | H | V | D | whole | residual |
|---|---|---|---|---|---|
| default | 59.3 | 36.4 | 168.3 | 278.6 | **+14.6** |
| `MALLOC_MMAP_THRESHOLD_=131072` | 59.3 | 36.3 | 168.3 | 257.7 | **−6.2** |
| `MALLOC_ARENA_MAX=1` | 59.3 | 36.4 | 168.3 | 268.6 | +4.6 |
| mmap + trim pinned | 59.3 | 36.4 | 168.3 | 257.7 | −6.3 |

Pinning the mmap threshold removes the residual and flips it to the negative
sign non-coinciding peaks predict. The mechanism is glibc's dynamic
`M_MMAP_THRESHOLD`: freeing an mmap'd block RAISES the threshold (up to 32 MB),
after which comparably sized allocations come from the sbrk arena instead —
and arena memory is trimmed only from the top, so it stays resident. In `pop`
the `u32v` reallocs free large mapped blocks and push the threshold up; the
dictionary's later table doublings then land in the arena. Run either structure
alone and the trajectory differs, which is why the parts under-predict.

Pinning also buys 21 B/triple outright (278.6 → 257.7). That is an environment
variable, not a code change, and adopting it is a decision this intent did not
take.

**A measurement-harness defect caught while doing this.** The first
decomposition script ran all four modes from one Python process.
`getrusage(RUSAGE_CHILDREN).ru_maxrss` is a running MAX over every child ever

order of footprint. The table above spawns exactly one child per process, the

across arms with different heap states; and the 21→40 swing between rep counts
tracks the array outgrowing cache, which is a memory-hierarchy term rather than
a crossing one. Hoisting the range out of the timed region is the fix; it is
new code and was not authorised at this gate.

different session, and cross-session ns are not comparable — printing them
adjacent would invite exactly the comparison the rule forbids.

30 ns marginal, at ~20 probes per range lookup, is ~600 ns of crossing —
**M1-side binary search is viable** and no range primitive is warranted. Note
what that 600 ns is NOT: it is a small fraction of the ~5,145 ns fixed cost
above, which is where the one-result patterns actually go.

### Method note: an artifact that looked exactly like the failure mode

An earlier `rt_bench_all` ran the isolated name-index sweep and a full
enumeration *before* the pattern timings. Each allocates and frees ~n entries,
and the timings that followed measured the resulting heap as much as the
structures. `S??` then read 46 µs/op at 10k and **272 µs/op at 1M** — a 5.9×
rise, reproducible across runs, and exactly the shape a superlinear descent
would produce.

It was not one. The `locality` mode — same population, same query, no prelude —
gives 47 µs/op at 1M. Reordering `rt_bench_all` so nothing allocates at
population scale before the pattern timings removed it, and the numbers above
are from the corrected harness.

Worth recording because the wrong reading was available and plausible: the
quadratic signature is ~1000× across this range (369 s vs 252 ms at 100k in the
list-fold finding), not 5.9×, and the per-result cost of the two genuinely
result-proportional patterns stayed flat throughout — which was the evidence
that the descent was linear all along.

## Durable tier (P3, AXVERITY_FORMAT_LAND_AND_WIRE_V1)

The section that used to sit here said durability was out of scope because
"durable blocks have no record framing and no stable block id — `seq` mints
from 0 each run and the filename is a pure function of it, so run 2 overwrites
run 1's block-0. A durable name -> RID map would be *wrong* after restart, not
stale." F1v gave records boundaries and B1 gave blocks identities that survive
a restart, so both obstacles are gone and the map is now well defined.

```
rt-driver rebuild        # cold rebuild from .axverity-store — BOTH streams
rt-driver cold <n> [lv]  # rebuild, then assert every pattern against the corpus
rt-driver rid <name>     # rebuild, then name -> RID -> record
rt-driver coldbench <n>  # rebuild, then time patterns and point reads
rt-driver ordbench <n>   # point-read cost across a block (pre-5b: by ordinal)
```

**No write-path tap.** The read tier still takes no channel from the `wp_*`
pipeline and is still launched by nobody. It does not need one: the durable
store is a shared artefact rather than a channel. The write path publishes a
liveness hint on `wp-durable-block` (a depth-1 mailbox that cannot stall the
writer), but the durable store on disk is the source of truth. The write path
was not modified to make this work — `experiments/format/check-hashes.sh` is
part of the durable suite.

**THE REBUILD READS BOTH STREAMS.** This file used to say "the structure stream
is the source of truth and the rebuild reads only that", and that was W1: a
record routes to `payload/` when it exceeds `wp_stream_threshold` (32 bytes),
nothing about a graph record keeps it under 32 bytes — three names averaging
ten characters are already over — so a structure-only scan silently dropped
every triple a real consumer emits. Measured: **0 of 13,000 records indexed**
on a realistic corpus. It was admitted, counted, written durably, and invisible
to every query. Closed by `AXVERITY_SILENT_LOSS_FIX_V1`; the full measurement,
including why S2's "structure-only replay is 23-25x faster" justification is
retired, is in `experiments/silentloss/FINDING-S2-RATIONALE.md`.

The two streams share no id sequence — each is dense on its own, and a block id
alone does not name a file (see the RID formula below) — so folding the union
cannot index a block twice.

**A RID is one integer, and it names a record.**

```
rid    = (seq * 2 + stream) * stride + offset

offset = rid % stride            stride = the block capacity IN BYTES,
stream = (rid / stride) % 2               read from .axverity-store/block_capacity
seq    = (rid / stride) / 2               (rt_rid_stride.m1)
```

Packed arithmetically, decoded with three divisions, no stored mapping. This is
what B1 bought over a scheme that resolved 1,028x faster: one integer still
names one record.

**Two things in that formula replaced earlier ones, and both were forced by
measurement rather than taste** (`AXVERITY_EXTENT_WRITE_PATH` step 5b):

- **`offset` is a BYTE OFFSET, not an ordinal.** An ordinal had to be RESOLVED
  BY SCANNING — walk records from the block's start counting to the wanted one,
  with the block staged in full first. Measured on a full 16 MiB block: 25.3 ms
  before a single scan step, then 5.77 µs per ordinal — ~160 ms for an average
  record and ~295 ms for the last, against **676 ns** for a direct pread. The
  ordinal scheme was viable only while blocks were 16 KiB.
- **`stream` is IN the locator.** Without it `rt_dblk_path` had to guess which
  directory held the block, at 1,657–1,847 ns per `fs_file_exists` probe — a
  payload lookup spent ~3.5 µs deciding where to look, five times the read it
  enabled. And once slablock minted per-handle sequences the guess became
  WRONG, not merely slow: `structure/block-36.bin` and `payload/block-36.bin`
  both exist, with different sizes and hashes, and the probe order silently
  picked one.

**The stride no longer needs an overflow assertion, and that is the point.**
The old ordinal stride was a fixed 16384 that an ordinal could in principle
reach, aliasing two records onto one RID, so it was asserted at scan time
(`FATAL rid_ordinal_overflow`). A byte offset is below the stride BY
CONSTRUCTION — the stride IS the block capacity and a block's payload is at
most capacity − 8 — so the thing being bounded and the thing defining the bound
are the same number. The old scheme had to be argued about and checked; this
one cannot alias.

**Read the stride from the STAMP, never from config.** `.axverity-store/block_capacity`
records what this store's blocks were actually WRITTEN at; `config/block_capacity`
says what someone wants the NEXT store to use. Decoding must follow the bytes on
disk. The `16384` fallback in `rt_rid_stride` when no stamp exists is the LEGACY
value for stores written before the stamp — it is not a copy of the default,
which is 4194304 now, and must not be updated with it.

**A spanning record's locator is the ordinary shape, and resolving it is not.**
A record too large for a block is written UNFRAMED across consecutive blocks, so
it begins at offset 0 of its first block and gets `(seq, stream, 0)` like
anything else. But there is no length prefix at that offset — the payload is raw
body bytes — so `rt_read_rid` reads the block's 8-byte footer BEFORE it trusts
the offset, and hands a spanning record to `rt_span_text` / `rt_span_total`,
which walk the chain. Decoding a varint there anyway is silent and was: a 10 MB
record indexed under three names read back as `len=100`, because its subject
happened to start with `d` (0x64).

**The index is rebuilt, not checkpointed.** `rt:ridx` maps a name to a durable
RID, but the map itself lives in RAM and is reconstructed from the structure
stream on cold start. Index checkpointing is deliberately a later intent. The
RID a name resolves to is the SMALLEST it appears at: `fs_list_dir` returns a
directory in arbitrary order, so "first wins" would make the index depend on
filesystem order and two rebuilds of one store could disagree. Minimum is
order-independent, so the index is a pure function of the durable bytes.

**Decoding goes through raw memory, never the Bytes API.** `Value::Bytes` is a
plain `Vec<u8>` with no structural sharing and `bytes_get` is declared
`vec![Bytes, Int]` with its argument emitted as `.clone()` — per-byte access
copies the whole block, making a scan O(N²). This is the `Value::List`
fold hazard in its Bytes twin. A block is staged once with one `mem_write_raw`
and never named again.

### The lazy seal is invisible in `coldbench`, and here is its size

`rt_rebuild` only APPENDS. Nothing queries during a rebuild, so the whole-array
sort lands on the first query afterwards — which in `rt_coldbench` is rep 1 of
its first timed pattern. Two consequences, both measured at n=100,000 against a
store written by a real `wp-slice` process:

| | ns/op |
|---|---|
| `coldbench` `S??` — FIRST pattern, carries the seal | 24,251 |
| `coldbench` `??T` — second pattern, seal already paid | 15,019 |
| RAM `bench` `S??` — seal paid inside `rt_populate` | 14,975 |

The first pattern is inflated by **9,276 ns/op**, i.e. **+62%**. Over 1,000 reps
that is 9.28 ms, against `seal_ms=9` measured independently at the same
population — the same number, arriving in the wrong column.

`rebuild_ns` correspondingly UNDER-reports: 479 ms at 100k excludes a 9 ms seal,
so a cold rebuild is ~1.9% dearer than it prints. (For scale, that 479 ms is
against the trie's 3.66 s at the same population.)

Neither is fixed here. The one-line fix — `rt_seal` at the end of `rt_rebuild`
— would move the cost into `rebuild_ns` where it belongs and leave the pattern
timings clean, but it is a code change and this gate authorised none.

**Point reads: a scan, and the price of having no per-block directory.**

> **SUPERSEDED by step 5b — kept for the defect it caught, not for its
> numbers.** Everything in this subsection measures the ORDINAL locator, which
> no longer exists: a RID carries a byte offset now and a point read is a
> direct pread at ~676 ns, so the k x 985 ns walk below is not a cost anything
> pays. The trailing-directory argument it makes goes with it — the ~50x a
> per-block directory would have bought was 50x of a scan that was deleted
> instead. **F2 is closed by the locator change, not by a directory.** What
> survives is the last paragraph: a flat curve was the signature of a missing
> early exit, and that reasoning is worth keeping.

Block 0, fixed ordinal, so locating the file costs the same in every row:

| ordinal | ns/read |
|---|---|
| 0 | 15,917 |
| 200 | 213,348 |
| 400 | 407,909 |
| 800 | 803,916 |

Linear at **~985 ns per record skipped** on a **~16 µs** fixed cost (locate,
open, stage). F1v frames each record with a length and nothing else, so
reaching record k means decoding the k before it. At a mean ordinal of ~800 for
a structure block, a full `name -> RID -> bytes` round trip measures
**478-593 µs**, population-independent — it depends on records-per-block, not
on store size.

**This WAS the read-side case F2 was waiting for, and step 5b answered it a
different way.** The trailing-directory candidate was rejected on write-side
numbers with its claim explicitly recorded as untested: "one tail seek gives
every boundary without touching payload, and P1 did not measure the read side."
A directory would have replaced the k x 985 ns walk with a seek, i.e. roughly
the 16 µs fixed cost — about 50x at the mean ordinal, growing with block
capacity.

Putting the BYTE OFFSET in the locator removed the walk entirely instead, and
did better than the directory would have: **676 ns**, not 16 µs, because there
is no block to stage and no boundary table to consult. It also costs nothing on
the write side and adds no durable structure. Do not re-open F2 on the strength
of the table above — it prices a mechanism that is gone.

**A defect this measurement caught.** The first ordinal sweep came back *flat*
at ~1.17 ms for every ordinal, which looked like the fixed cost dominating.
It was not: mode-1 scans had no early exit and walked the whole block even
after finding their record. The flatness was the signature. With the exit,
ordinal 0 is **73x faster** (15.9 µs vs 1.17 ms) and the linear shape above
appears. A rising cost was the expected result; a flat one is what showed the
bug.
